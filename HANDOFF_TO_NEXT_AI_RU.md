# Передача проекта Living Villages следующему ИИ-разработчику

## Цель

Продолжить разработку мода Minecraft Java Edition 1.21.1 на NeoForge 21.1.x / Java 21. Рабочее название Living Villages. Цель — самостоятельная деревня с настоящими материалами, профессиями, строительством, экономикой, размножением и управлением через старосту.

## Главные правила

1. Сначала внимательно изучить проект и запустить доступные проверки. Не переписывать всё с нуля без причины.
2. Не выдавать статическую проверку или проверку ZIP за компиляцию. Не заявлять, что мод работает в игре, пока `./gradlew build` проходит, а игровые сценарии проверены в `runClient`.
3. Не создавать ресурсы из воздуха. Добыча, строительство, крафт, посадка, экипировка и еда должны использовать реальные предметы/блоки, дроп, рецепты и инвентари Minecraft.
4. Использовать обычную навигацию жителей; не телепортировать их, не ломать блоки на расстоянии и сквозь стены.
5. Все изменяющие мир операции выполнять на сервере, учитывать мультиплеер, сохранение мира и производительность.
6. Сохранять ванильные профессии, торговлю и уровни жителей. Новые роли (лесоруб, шахтёр, строитель, защитник, курьер и т.п.) — дополнительные назначения, не замена профессии.
7. Все игровые настройки должны быть доступны через меню модов; не полагаться на команды в чате.
8. После каждого небольшого этапа запускать сборку/тесты, смотреть ошибки и обновлять `CHANGELOG_RU.md`, `README_RU.md` и `TEST_REPORT_RU.md`.
9. При изменениях файлов выполнять `python3 tools/validate_project.py`, `java tools/JavaSyntaxCheck.java src/main/java`, статические тесты из `tools/` и `./gradlew build`, если есть сеть.
10. Если сборка не запускается из-за сетевого ограничения, сообщить это прямо и не делать вывод, что код компилируется.

## Текущее состояние архива 0.15.0

- Конфигурация на Minecraft 1.21.1, NeoForge 21.1.264, Java 21, mod id `livingvillages`.
- 16 Java-файлов, включая основной класс, клиентскую регистрацию, конфиг, характер/память, роли, лес, шахтёра, защитника, фермерскую логистику, производство, строительство, население и старосту.
- Экран старосты открывается взаимодействием с обычным жителем. Староста должен сохранить ванильную профессию. Панель предназначена для статуса поселения, переключения приоритета/автономности и выдачи строительных заказов.
- Есть логика реальных затрат ресурсов для ряда цепочек: древесина → доски → сундук/верстак → инструменты; руда/топливо/печь; поэтапное строительство дома; фермерский участок; добыча с реальным дропом; курьер еды для естественного размножения.
- Есть статические проверки и тесты в `tools/`, включая проверку материальной ведомости дома/фермы, политики старосты и населения.

## Важные оговорки

- В этом архиве нет готового JAR. Статическая проверка Java не проверяет наличие всех корректных типов/методов в classpath Minecraft/NeoForge.
- `gradlew`/`gradlew.bat` в текущем проекте — checksum-проверяемый bootstrap, который загружает официальный Gradle 9.2.1 при наличии сети; это не стандартный wrapper с `gradle-wrapper.jar`. Для первой настоящей проверки необходимо интернет-соединение к `services.gradle.org` и репозиториям Gradle/Minecraft/NeoForge.
- Полная компиляция и `runClient` на момент упаковки не подтверждены. Предыдущая попытка остановилась на DNS при обращении к `services.gradle.org`.
- Некоторые заявленные механики могли быть проверены только статическими тестами. Проведи честный аудит реального кода и не считай README доказательством работоспособности.

## Приоритеты следующей работы

### P0 — игровая проверка уже собираемой версии
1. `./gradlew build`, статические проверки и запуск dedicated server прошли в GitHub Actions для commit `327bd5346c278dfd433d4d6e67bae1e41efb3707`: [результат CI](https://github.com/aba04-stack/Minecraft-mod/actions/runs/40284992624).
2. Запустить `runClient` и проверить открытие/закрытие экрана старосты, server-side actions и отсутствие client-only ссылок на dedicated server.
3. Собрать два близких поселения в тестовом мире и проверить поведение жителей, заказов и интерфейса. Статические тесты не заменяют эту проверку.

### P1 — довести изоляцию поселений и общую экономику
1. Первый этап группировки уже добавлен: `VillageArea` предпочитает ванильные HOME-точки, ограничивает группировку и выбирает ближайшую группу; ключевые подсистемы используют общий селектор.
2. Обязательно проверить две соседние деревни в игре. Сейчас это эвристика для загруженной области, а не постоянный глобальный реестр; сундуки, кровати, рабочие блоки и участки всё ещё не гарантированно принадлежат только одной деревне.
3. Начальная система резервирования физических контейнеров уже добавлена: заявки записываются в persistent data рабочего, конфликтующие задачи пропускают занятые сундуки, новый контейнер захватывается до маршрута, освобождение проверяет тип задания.
4. Это блокировка целого сундука, а не per-item ledger; она действует в пределах загруженных окрестностей и может временно задерживать другие задачи. Нужны игровые тесты, обработка сломанных контейнеров и восстановление резервов после гибели работника.
5. Дом/ферма также проверяют активные строительные площадки перед поиском участка и стартом проекта, чтобы две близкие группы жителей не начали строить в одной точке.
6. Поиск физических хранилищ теперь проверяет пересечение HOME-групп у запрашивающего поселения и у сундука. Это лучше, чем один радиусный поиск, но остаётся эвристикой без постоянного реестра; обязательно проверить два поселения с пересекающимися радиусами в `runClient`.
7. Добавить сохраняемую идентичность поселения и привязать сундуки, кровати, рабочие блоки и участки к конкретной деревне.
8. Освобождать занятую роль при отключении соответствующей настройки, исчезновении инструмента/рабочего блока, смерти/ухода жителя или паузе проекта.
9. Сделать однозначные состояния заказа: `PENDING`, `RESERVED`, `FETCHING`, `WORKING`, `WAITING_FOR_RESOURCES`, `DELIVERING`, `DONE`, `CANCELLED`.

### P2 — строитель и геймплейный первый цикл
1. Строить дом/ферму по одному безопасному блоку; не перезаписывать чужие блоки; учитывать дверь, свет, кровать, доступ жителей и безопасный путь.
2. Сохранять чертёж и этап строительства после перезапуска мира/перехода чанка.
3. Все проекты (дом, ферма, склад, мастерская) должны использовать один движок чертежей и настоящую стоимость материалов.
4. Староста выбирает проекты по нуждам: еда, жильё, склад, инструменты, защита. Если ресурсов нет, проект ждёт — ничего не появляется из воздуха.

### P3 — экономика и профессии
1. Сохранить 13 ванильных профессий и торговлю. Добавлять дополнительные рабочие роли через общий планировщик.
2. Реализовать короткую, полностью проверяемую цепочку: лесоруб → склад → ремесленник/верстак → кирка → шахтёр → руда/булыжник → печь + топливо → слиток → инструменты/оборона.
3. Транзакции инвентарей должны быть атомарными: сначала проверить входы и место результата, затем расходовать/перемещать; при неудаче вернуть предметы.
4. Для размножения опираться на ванильный AI, свободные кровати и реальную еду; не создавать детей скриптом.

### P4 — тестирование
- Компиляция: `./gradlew build`.
- Клиент: `./gradlew runClient`.
- Проверить одиночный мир, выделенный сервер, минимум две близкие деревни, заполненные сундуки, недостаток материалов, выключение ролей, смерть рабочего, незагруженные чанки, `mobGriefing=false`, занятый/сломанный рабочий блок, полное хранилище и повторную загрузку мира.
- Сохранять доказательства реальных тестов: команды, краткий вывод сборки, ошибки/лог, точный путь к JAR.
