# Передача проекта Living Villages следующему ИИ-разработчику

## Цель

Продолжить разработку мода Minecraft Java Edition 1.21.1 на NeoForge 21.1.x / Java 21. Рабочее название Living Villages. Цель — самостоятельная деревня с настоящими материалами, профессиями, строительством, экономикой, размножением и управлением через старосту.

## Главные правила

1. Сначала внимательно изучить проект и запустить доступные проверки. Не переписывать всё с нуля без причины.
2. Не выдавать статическую проверку или проверку ZIP за компиляцию. Не заявлять, что мод работает в игре, пока `./gradlew build` проходит, а игровые сценарии проверены в `runClient`.
3. Не создавать ресурсы из воздуха. Добыча, строительство, крафт, посадка, экипировка и еда должны использовать реальные предметы/блоки, дроп, рецепты и инвентари Minecraft.
4. Использовать обычную навигацию жителей; не телепортировать их, не ломать блоки на расстоянии и сквозь стены.
5. Все изменяющие мир операции выполнять на сервере, учитывать мультиплеер, сохранение мира и производительность.
6. Сохранять ванильные профессии, торговлю и уровни жителей. Новые роли (лесоруб, шахтёр, строитель, защитник, курьер и т.п.) — дополнительные назначения, не замена профессии.
7. Все игровые настройки должны быть доступны через меню модов; не полагаться на команды в чате.
8. После каждого небольшого этапа запускать сборку/тесты, смотреть ошибки и обновлять `CHANGELOG_RU.md`, `README_RU.md` и `TEST_REPORT_RU.md`.
9. При изменениях файлов выполнять `python3 tools/validate_project.py`, `java tools/JavaSyntaxCheck.java src/main/java`, статические тесты из `tools/` и `./gradlew build`, если есть сеть.
10. Если сборка не запускается из-за сетевого ограничения, сообщить это прямо и не делать вывод, что код компилируется.

## Текущее состояние архива 0.15.0

- Конфигурация на Minecraft 1.21.1, NeoForge 21.1.264, Java 21, mod id `livingvillages`.
- 20 Java-файлов в `src/main/java`, включая `VillageRegistry`, общий селектор групп, тесты резервирования, резервы контейнеров, характер/память, роли, лес, шахтёра, защитника, логистику, производство, строительство, население и старосту.

- Есть логика реальных затрат ресурсов для ряда цепочек: древесина → доски → сундук/верстак → инструменты; руда/топливо/печь; поэтапное строительство дома; фермерский участок; добыча с реальным дропом; курьер еды для естественного размножения.
- Есть статические проверки и тесты в `tools/`, включая проверку материальной ведомости дома/фермы, политики старосты и населения.

### Баг-хант `0.17.0`: логистика и наряды-заказы (коммиты `ffbe242` → `1bb0e7e` → `e86ebc3`)

- **Найден краш сервера в уже собранном коде.** `VillageWorkOrders.pendingMaterialPickupDeficits` возвращает `Map.copyOf`, а `VillageLogistics.collectNearbyMaterials` вычитал собранные количества из этой же карты. Как только у поселения появлялся открытый заказ с реальным дефицитом и курьер подбирал нужный дроп, `put` бросал `UnsupportedOperationException` внутри `EntityTickEvent.Post` — падение с отчётом «Ticking entity». В фикстурах заказов не было, карта приходила `null`, и выполнялся запасной путь, поэтому 54 теста дефект не видели.
- Правило на будущее: **то, что возвращает другая подсистема, менять нельзя**. `Map.copyOf`/`List.copyOf`/`Set.copyOf` в этом проекте — контракт «только чтение». Курьер теперь делает свою копию (`new HashMap<>(deficits)`), а `collectPendingMaterials` — публичный тестовый шов (GameTest не умеет порождать событие тика сущности).
- **Вторая находка в том же методе:** подбор игнорировал ванильную задержку поднятия, поэтому курьер мгновенно забирал стопку, которую игрок только что выбросил (у игрока есть 40 тиков, чтобы поднять её обратно; собственная передача еды в моде ставит 10).
- **Особенность маппингов 1.21.1 (проверено двумя падениями CI):** у `ItemEntity` нет публичного геттера задержки — `getPickUpDelay()` не существует ([run 42461971894](https://github.com/aba04-stack/Minecraft-mod/actions/runs/42461971894)), а поле `pickupDelay` приватное ([run 42462868259](https://github.com/aba04-stack/Minecraft-mod/actions/runs/42462868259), сообщение компилятора `pickupDelay has private access in ItemEntity`). Публичны только `setPickUpDelay(int)` и `setNoPickUpDelay()`. Значение читается из NBT сущности: `saveWithoutId(tag)` → `tag.getShort("PickupDelay")`; ключ подтверждён патчем NeoForge `patches/net/minecraft/world/entity/item/ItemEntity.java.patch` для ref `1.21.1`. Проверка стоит после фильтра по типу предмета, поэтому сериализация выполняется только для релевантных дропов.

### Баг-хант `0.17.0`: животноводство, фермер и строитель (коммит `b6abd4a`)

- **Найдена потеря данных предметов.** Все переносы «склад поселения → инвентарь работника» удаляли N предметов по количеству и создавали с другой стороны `new ItemStack(item, N)`. Для материалов это эквивалент, для предмета с данными — уничтожение ценности: изношенные ножницы/мотыга приходили новыми (бесплатный ремонт из ничего), зачарования, имена, цвет и содержимое шалкер-бокса пропадали из сохранения. Тот же пересбор был в порту `VillageRegistry.transferItem`.
- **Общий помощник `VillageItemTransfers`** (`moveRealItems`, `insertReal`): переносит реально лежащие стеки, отказ возвращает тем же стеком в тот же контейнер, роняет только то, что контейнер тоже не принял. Использует только примитивы `Container` (`getItem`/`setItem`/`removeItem`/`canPlaceItem`/`getContainerSize`/`getMaxStackSize`), поэтому работает и для `SimpleContainer` жителя, и для сундука/бочки.
- Переведены: `VillageLivestock.transferFromStorage`, `VillageFarmBuilder` (материалы и мотыга), `VillageBuilder` (материалы), `VillageRegistry.transferItem` (с откатом частичного переноса — контракт порта транзакционный). Удалены ставшие мёртвыми `removeItem` (Livestock), `rollbackOrDrop` (FarmBuilder), `insertStack` (Builder).
- **Осознанно не переведены** (зафиксировано в KI-016): ингредиенты крафта `VillageCraftingJobs` (предмет уничтожается рецептом) и посадочные предметы `VillagerAutonomy.withdrawPlantingItems` (семена/морковь/картофель/свёкла не несут компонентов). Если там появятся инструменты или предметы с компонентами — переводить на `VillageItemTransfers`.
- Проверено и НЕ оказалось багом: `claimSheepAfterHerding` требует свежую запись приманивания (овца не «присваивается» просто за нахождение в загоне), `isInsideExistingFencePen` защищает чужой огороженный выпас, `shearManagedSheep` стрижёт только свою овцу в загоне настоящими ножницами и списывает их прочность, геометрия загона (`site` — угол 5×5, калитка `site.offset(2,0,0)`, интерьер 3×3) согласована между `hasCompletePen`, `isInsideVillagePen`, `penCenter`, `penGatePosition` и AABB в `claimSheepAlreadyInsidePen`.

### Perf-цикл 2 `0.17.0`: поиск склада работником (коммиты `6f274b1` → `82d28a8`)

- Причина: наблюдение баг-ханта животноводства оказалось измеримой стоимостью. Обе подсистемы работников отвечали на «к какому складу идти?» полным обходом коробки хранилищ и сортировкой всех кандидатов: курьер — `33×33×9 = 9 801` прочтений на каждую попытку доставки, животновод — `33×33×13 = 14 157` и до четырёх A*-путей на **каждого** кандидата.
- Общий метод `VillageScanRings.nearestInBox(origin, boundsCenter, boundsRadius, downReach, upReach, accept)`: кольца наружу от работника, выход на первой принятой предикатом позиции. Кандидаты — строго коробка вокруг центра владения (колонки вне неё отсеиваются целочисленным сравнением, без чтения чанка и состояния блока), радиус колец — `boundsRadius + max(|dx|, |dz|)` от работника до центра, поэтому работник на краю поселения по-прежнему видит дальние склады.
- Переведены: `VillageLogistics.findNearestStorageWithRoom`, `VillageLivestock.findNearestStorageWithItem` и `findNearestStorageWithWoolRoom` (новые помощники `storageRadius`, `acceptsStorageWithItem`, `acceptsStorageWithWoolRoom`, `acceptsStorage`). **`findStorages` сохранён** — он нужен в двух местах, где требуется обойти все склады (подсчёт настоящих ножниц и снимок запасов); контракт `tools/test_resource_reservations.py` пинит его использование в `VillageFarmBuilder`, не ломать.
- `findSafeStand`: безопасные стороны сортируются по дистанции до работника, A* строится только до первой достижимой — результат прежний («ближайшая достижимая точка стояния»), путей обычно один вместо четырёх.
- Единственное поведенческое отличие: между равноудалёнными складами может быть выбран другой (порядок колец вместо порядка сортировки). Оба вызывающих считают их взаимозаменяемыми.
- **Отклонённый кэш:** `hasCompletePen` (16 граничных позиций = 32 чтения на вызов) оставлен без кэша. Причины: стоимость несопоставима с обходами выше; точки инвалидации нет (забор ломает игрок или взрыв, а не код мода); существующие тесты загона (`VillageReservationGameTests`, примерно строки 2997 и 3155–3172) ставят и убирают блоки и переспрашивают `getPenRepairPlan`/`hasCompletePen` в том же тике. Объём работы записан в `docs/PERFORMANCE_BUDGETS.md` раздел 3.2 — не возвращайся к идее кэша без новой точки инвалидации.
- Новый тест `nearbyDeliveryStorageIsFoundWithoutWalkingTheWholeStorageBox` (batch `scan_budget_storage`, всего 57 `@GameTest`): настоящий собственный сундук в двух блоках от курьера с настоящими 8 брёвнами в инвентаре — `207` из `9 801` прочтений; после удаления сундука — ровно `9 801` (покрытие не сузилось).
