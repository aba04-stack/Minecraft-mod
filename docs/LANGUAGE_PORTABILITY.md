# Архитектура переносимости основной логики на другой язык программирования (`LANGUAGE_PORTABILITY`)

> **Текущий статус:** `PLANNED` (в прототипе `0.15.0` бизнес-правила и вызовы Minecraft/NeoForge API объединены в классах пакета `com.abs.livingvillages`).

> **Связанные документы:** [Целевая архитектура (`ARCHITECTURE.md`)](ARCHITECTURE.md) · [Техническое задание (`PROJECT_SPEC.md`)](PROJECT_SPEC.md) · [Адаптеры версий (`VERSION_ADAPTERS.md`)](VERSION_ADAPTERS.md) · [Инженерные стандарты (`ENGINEERING_STANDARDS.md`)](ENGINEERING_STANDARDS.md) · [Тестирование (`TESTING.md`)](TESTING.md)

## 1. Цель архитектурной переносимости

Цель проектирования переносимости в **Living Civilization** — отделить расчётное ядро симуляции (экономику реальных ресурсов, ведомости чертежей, очереди заказов, приоритеты старосты, прокачку профессий и автоматы принятия решений ИИ) от платформенных классов Minecraft и загрузчика NeoForge так, чтобы при необходимости переноса основной логики на другой язык программирования (или в отдельную среду исполнения) **не требовалось заново проектировать каждую игровую систему с нуля**.

## 2. Архитектурные требования к переносимому ядру (`PLANNED`)

### 2.1. Изоляция доменного слоя от платформенного API

1. **Запрет платформенных импортов в ядре (`com.abs.livingvillages.domain`):**
   - Классы ядра не должны импортировать `net.minecraft.*`, `com.mojang.*`, `net.neoforged.*`, `io.netty.*`.
   - Все вызовы к миру Minecraft, блокам, сущностям и контейнерам выполняются исключительно снаружи ядра через чётко определённые порты и адаптеры (`com.abs.livingvillages.ports` / `platform`), см. [`ARCHITECTURE.md`](ARCHITECTURE.md).
2. **Запрет передачи объектов Minecraft внутрь ядра:**
   - В методы доменного слоя нельзя передавать `Villager`, `Mob`, `ServerLevel`, `BlockPos`, `ItemStack`, `Container`, `BlockEntity`, `CompoundTag` или внутренние объекты загрузчика.
3. **Простые модели данных (DTO) и стабильные идентификаторы:**
   - Граница между адаптером и ядром использует плоские неизменяемые структуры данных (примитивы, строки, списки, записи `record`):
     - координаты передаются как простая тройка целых чисел `BlockCoord(int x, int y, int z)`;
     - сущности идентифицируются стабильными `UUID` (`AgentId`, `SettlementId`);
     - предметы и блоки идентифицируются каноническими строковыми ключами (`"minecraft:oak_planks"`, `"minecraft:raw_iron"`, `"minecraft:red_bed"`) или конечными доменными перечислениями;
     - количество предметов передаётся явными целочисленными картами/списками (`ItemQuantity(String itemId, int count)`).
4. **Независимые unit-тесты:**
   - Вся логика расчёта материальных ведомостей (например, 96 досок + дверь + кровать для дома, 24 семени + вода + компостер + мотыга для фермы), очерёдности кормления жителей, прогрессии уровней (1–5) и переходов состояний заказов должна покрываться unit-тестами, которые компилируются и выполняются на стандартной JVM без запуска Minecraft.
5. **Отказ от избыточных абстракций:**
   - **Не создаётся** собственный универсальный игровой движок, интерпретатор скриптового языка, виртуальная машина или межпроцессное взаимодействие (IPC/сокеты) без конкретной доказанной необходимости.

## 3. Выбор языка и форматов обмена данными

### 3.1. Отказ от преждевременного выбора нового языка

- В проекте **заранее не выбирается и не навязывается** конкретный второй язык программирования (Rust, Kotlin, C++, C# и т.д.), пока не проведён технический анализ и не подтверждена реальная потребность.
- Первоочередная задача — выстроить чистые границы зависимостей, контракты данных и тестовый набор внутри существующего Java-проекта.

### 3.2. Сериализация на границах без потери производительности

- Версионированные схемы данных (JSON, бинарные кодеки или табличные структуры) используются **только там, где это оправдано**:
  - при сохранении и загрузке состояния поселений и жителей ([`SAVE_DATA.md`](SAVE_DATA.md));
  - при чтении шаблонов чертежей, рецептов и таблиц баланса;
  - при обмене сетевыми пакетами между сервером и клиентом (`ElderPanelData`, `ElderAction`).
- **Строгое ограничение по производительности:** запрещено сериализовать в JSON/байтовые массивы каждую операцию игрового тика внутри одного процесса. Внутри JVM обмен между платформенным адаптером и доменным ядром происходит через легковесные DTO без лишнего копирования памяти и аллокаций (см. [`PERFORMANCE.md`](PERFORMANCE.md)).

## 4. Честное описание ограничений переносимости

Архитектурная переносимость **снижает связность кода и позволяет сохранить все спроектированные правила, алгоритмы, схемы данных и тестовые сценарии**, но **не делает перенос на другой язык автоматическим или бесплатным**.

При реальном переносе доменного ядра на другой язык программирования неизбежно потребуются следующие ручные работы:
1. **Перенос или компиляция кода ядра:** перевод чистых доменных модулей и их unit-тестов на целевой язык с проверкой идентичности поведения на одних и тех же тестовых векторах.
2. **Среда исполнения и мост (Runtime / Bridge):** если мод продолжает работать поверх Minecraft Java Edition, потребуется механизм вызова между JVM и новым языком (например, Java 21+ Foreign Function & Memory API / Project Panama, JNI или WASM-рантайм) либо полная интеграция в целевую платформу.
3. **Платформенные адаптеры Minecraft:** весь слой взаимодействия с API Minecraft/NeoForge (`ServerLevel`, события, навигация `Brain`, рендеринг GUI `Screen`, сетевые пакеты) остаётся привязанным к платформе игры и адаптируется вручную.
4. **Профилирование накладных расходов границы:** проверка того, что вызовы через межъязыковой мост не создают узких мест по MSPT и сборке мусора (GC).

## 5. Что уже можно переиспользовать из кода `0.15.0`, а что требует рефакторинга

| Компонент `0.15.0` | Готовность к выделению в чистое ядро | Что требуется сделать (`PLANNED`) |
|---|---|---|
| Материальная ведомость дома (`VillageBuilder`: 96 досок + дверь + кровать, геометрия 5×5) | Высокая (чистая геометрия и расчёт предметов) | Вынести генерацию шагов чертежа и проверку комплектности из `VillageBuilder` в `domain.blueprint.HouseBlueprint`. |
| Материальная ведомость фермы (`VillageFarmBuilder`: 24 культуры, 4 валидные пары семян/блоков, вода, компостер, мотыга) | Высокая | Вынести таблицу культур и последовательность шагов `FarmStep` в `domain.blueprint.FarmBlueprint`, заменив `Item`/`Block` на строковые ID. |
| Выбор получателя еды (`VillagePopulation`: минимум очков сытости + детерминированный tie-break по UUID) | Высокая | Вынести функцию ранжирования кандидатов `selectHungriestRecipient` в `domain.population`. |
| Правила назначения специалистов (`VillagerRoles`: квоты строителя, ремесленника, шахтёров, стражи) | Средняя | Отделить расчёт целевых квот от чтения `villager.getPersistentData()` и `ServerLevel`. |
| Автоматы состояний ремесла, логистики, лесоруба и шахтёра | Средняя | Заменить прямые обращения к `CompoundTag` и `WalkTarget` на доменные состояния `TaskState` и команды `TaskCommand`. |
| Панель старосты и сетевые пакеты (`VillageElder`, `LivingVillagesClient`) | Остаются в платформенном слое | Оставить кодеки `StreamCodec` и `Screen` в `platform`, вынеся в `domain` только валидацию переходов приоритета и очереди заказов. |

## 6. Критерии проверки архитектурной переносимости

Архитектура считается соответствующей требованиям переносимости только при выполнении всех пяти проверок:

1. **Автономная компиляция и запуск доменных тестов:** пакет `com.abs.livingvillages.domain` и его unit-тесты компилируются и проходят без подключения библиотек Minecraft и NeoForge.
2. **Контроль чистоты импортов:** статическая проверка подтверждает полное отсутствие строк `import net.minecraft.`, `import com.mojang.`, `import net.neoforged.` во всех файлах каталога `domain/`.
3. **Документированные и версионированные контракты данных:** все входные/выходные DTO между `domain` и `platform` аннотированы/описаны и имеют явную версию схемы для сохраняемых состояний.
4. **Раздельное тестирование адаптеров:** платформенные адаптеры проверяются отдельными интеграционными/игровыми тестами на корректность трансляции между объектами Minecraft и DTO ядра.
5. **Устойчивость ядра к изменениям Minecraft API:** обновление сигнатур методов Minecraft/NeoForge (например, изменение метода рендера экрана или сериализации NBT) требует правок только в `platform.*` и не затрагивает ни одного файла в `domain.*`.
